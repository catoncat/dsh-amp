## 4. 体验机制改进清单（现象/证据/受影响/机制建议/最小实现/验收）

### U1 完成"到达"而不是"被问到"（对应 DESIGN A1，本报告补体验证据）【已确认】
- **现象**：owner 只能靠 21 次轮询 + 4 个 bash 监视循环知道子任务状态，owner 一结束 turn 就彻底失聪。
- **证据**：§1 全表；L1038"`dsh-amp-run-4` **不在** jobs 注册表里"；L1041、L1297 人类原话；L1304 agent 自认"丑陋替代品"。
- **谁受影响**：两者。agent 浪费 461s+ 工具等待与大量上下文；人类看到的是"agent 在那儿干等/瞎转"。
- **机制建议**：`amp_run` 注册进 `ctx.jobs`（kind `amp-live`，`readOutput=absorb`、`done=settlePromise`、`cancel=finish(kill)`、`owner=调用方`）；job done 监听器同步 splice 一条**带归属与 run id** 的完成通知进 owner inbox，必要时开新 turn。
- **最小实现**：`lib/live.js` 的 `registerLiveTools` 中 `amp_run` 成功路径加 `ctx.jobs.start(...)`；`lib/index.js` 无需新增工具。通知文本含 `run`/`thread`/`stopReason`/`diagnostic`/产出路径。
- **验收**：真机 `amp_run` 一个 30s 任务，owner 结束 turn 后**不轮询**，30s 内 inbox 出现完成通知且含产出；重复旧会话行为（等待循环）不再出现。

### U2 失败事件主动推送 + 归属标注【已确认】
- **现象**：子代理被额度掐断，错误信息既到过 inbox 又被人类手动粘贴，但无结构无归属，人类必须追问"你收到了吗"。
- **证据**：额度错误全文在 transcript 出现 22 次（credits）+11 次（rate limit）；L878（inbox 收到原始报错文本）、L888/L948（人类粘贴）、L889/L941（人类追问）。
- **谁受影响**：两者。
- **机制建议**：把 Amp 的 `Request Failed` 类错误识别为**结构化失败事件**（`kind: 'quota'|'rate-limit'`、`run`、`thread`、建议动作），失败时主动 push 给 owner 与运行卡片，而不是混在 `stopReason:"error"` 的 diagnostic 字符串里等人读。
- **最小实现**：`lib/outcome.js` 的分类器增加 quota/rate-limit 识别（现成文案已实测）；`lib/live.js` 结算路径在 `diagnostic` 旁加 `failure: {kind, retryable, account}` 字段；U1 落地后随完成通知一起推送。
- **验收**：构造无余额账号发起 run，owner inbox 收到 `failure.kind='quota'` 的结构化通知；人类无需转述任何报错。

### U3 余额对 agent 不可见：池自动预检、failover、降级【已确认（策略为人类口述）】
- **现象**：额度失败后 agent 手动查号 7 次、人类口头指挥换号、定降级规则；抽象泄漏。
- **证据**：L903/L911/L983 人类原话；`amp_accounts` 7 次调用中 4 次带 `refresh:true`（L880/L1085/L1181/L1309）全发生在额度事件之后。
- **谁受影响**：agent（被迫管理余额）；人类（当调度员）。
- **机制建议**：run 启动前池做余额预检并选择"够用"的号；额度失败自动 `noteRefusal` + 换号重试一次；余额低于阈值时按策略自动降到低档 mode；`amp_accounts` 从 agent 常规工具降级为诊断用途（描述里注明"通常无需调用"）。
- **最小实现**：`lib/accounts.js` 已有 `noteRefusal`/`stale`，补 `preflight(mode)`（阈值常量，如 $1/`$2`）与 `onQuotaFailure` 回调；`lib/live.js` spawn 前调用，失败时换号重试一次并把两次选择都写进 `account` 字段历史。
- **验收**：把第一号余额配置为不足发起 run → 工具返回的 `account` 显示自动落到第二号，全程无 `amp_accounts` 调用、无人类介入。

### U4 被掐断不等于作废：产出增量落盘 + thread 续跑【已确认】
- **现象**：run-4（设计评审）跑了 27 轮被额度掐断，"报告一个字都没落盘"，只能从零重跑 run-5。
- **证据**：L1077（diagnostic：`numTurns=27 … You must have at least $1 …`，含可续的 `thread=T-…`）；L1157（run-5 提示词自述"第一次跑了 27 轮真实分析后被额度中断…报告一个字都没落盘"）。
- **谁受影响**：agent（重烧 27 轮额度与时间）；人类（等待翻倍、看到重复劳动）。
- **机制建议**：两条腿：(a) 给子代理的任务模板强制"先落盘骨架、每节即写"（run-5 已证明有效，应固化为 `artifact.js` 的默认行为）；(b) A2 落地后，额度失败的重试默认**同 thread 续跑**并携带已落盘路径，而不是新开 run。
- **最小实现**：`lib/artifact.js` 提供 `openArtifact(path)`（骨架+追加写）；`lib/live.js` 的 `amp_run` 接受 `thread`（A2），重试路径由 U2 的 `failure.retryable` 触发并自动带上原 thread。
- **验收**：人为掐断一个正在写报告的 run，重试后产物文件保留前次内容且 thread id 不变。

### U6 部署→生效回路的最后一步：漂移可见，重启不再靠人判断【已确认】
- **现象**：人类一天宣告 4 次重启，其中一次"只生效了一半"。
- **证据**：L232/L451/L476/L663；L448"这次重启**只生效了一半**"；指纹机制已被证明有效（L676 零成本核对通过）。
- **谁受影响**：两者（人类当扳手；agent 反复自证）。
- **机制建议**：利用现成的运行时指纹（F20 已建），在工具输出与设置页常驻**磁盘源 hash vs 运行 hash** 的对比位；不一致时 `amp_run` 等入口在响应头部给一行"⚠️ 部署漂移：改动未生效，需重启"。
- **最小实现**：`lib/source.js` 已自报 `source{file,hash}`；`lib/web.js` 设置页加磁盘 hash（读 `node_modules/dsh-amp` 副本）与运行 hash 的 diff 徽标；`lib/live.js` 各工具响应加同一次比对（缓存，每次进程生命周期算一次）。
- **验收**：改源码不部署 → 任意 amp 工具响应出现漂移警告；`deploy.sh` + 重启后警告消失且 hash 一致。

### U7 steer 的存在感【已确认（低频）】
- **现象**：全程 10 个 run 只有 1 次真正的 steer 插话，人类却明确要求"和他一起配合工作"。
- **证据**：L853（唯一一次 `steer:true` 带消息）；L1194 人类原话。
- **谁受影响**：agent（配合流缺失）；人类（期望落空）。
- **机制建议**：U1 落地后，idle 通知里带"可 steer/可续跑"提示与 `thread` 参数，使"插话改向"成为完成通知后的默认动作而非冷知识。
- **最小实现**：完成通知模板加一行 `steer: amp_send_message({run, message}) 或续跑: amp_run({thread})`。
- **验收**：一次真实评审中途改向：steer 消息出现在子代理最终报告的"已吸收修改"里。

### U8 扇出：等单个，不等全部【已确认】
- **现象**：最后两个并行子任务用一个大 bash 循环同时盯，先完成的被后完成的遮蔽。
- **证据**：L1295（单循环同时盯 pgrep+两个产物大小，48 轮）；L1297"为什么一直等所有呢？…你好像也只能这样了"；L1250"你可以派多个"。
- **谁受影响**：两者。
- **机制建议**：per-run 完成通知（U1）天然解决；配合 U4 的产物落盘，先到先读。
- **最小实现**：无额外代码，依赖 U1；唯一加法是测试里造两个不同时长的 run 验证通知各自到达。
- **验收**：两个 run 分别 10s/60s 结束，两条通知间隔 ≈50s 先后到达，而非 60s 后一起到。

（文风类，最多两条，仅记录）【疑似】：(a) agent 把 deploy 方案 A/B 抛给人类决策（L681/L684）——机制上应是"低风险实现选择自行决定并说明理由"；(b) 轮询结果里 `idleMs` 等字段对人类不可读，属卡片化（B2）范围，已有评审覆盖，不展开。

## 5. 已确认好用的部分（不许改坏）【均已确认】
1. **诚实的失败诊断**：L1077 一条 diagnostic 同时给出 `stopReason/subtype/numTurns/thread/error`，是本次所有额度问题可归因的唯一依据。`quiescence`/"不撒谎的 `delivered`"契约在真机上没穿帮。
2. **运行时代码指纹**（F20 闭环）：`source{file,hash}` 让"我到底跑的哪份代码"变成零成本调用（L669–L676），并当场识破"重启只生效了一半"（L448）。
3. **deploy.sh 逐字节校验 + 预告指纹**：部署正确性有了机器答案，人类不再肉眼对。
4. **冷启动 hint 与增量读取**：`amp_send_message` 的冷启动解释、`idleMs/bytesSeen/unparsedLines` 让"思考中 vs 卡死"至少有数据可看（F1/F3 修复后无半行丢失）。
5. **结算幂等**：真机上并发两次 `amp_stop`（L503/L505）未挂、未谎报（F4 修复生效）。
6. **bash 任务走 jobs registry**：`job_output wait:true` 是"正确的等待"长什么样——U1 只是把 amp run 拉齐到这个水准（L882/L1123/L1137/L1152）。
7. **产物落盘契约**：run-5 的"先落盘骨架、每节即写"在第二次被掐断时保住了全部工作（L1157），是全场唯一让 27 轮成果可回收的模式。

## 6. 用出来的缺陷 vs 审出来的缺陷，及派单策略含义
- **用出来的**（本 session 实测发现）：F2/F3（轮询与冷启动）、F20（部署不生效）、F21（结算吞消息）、F7（ledger 脱节）、F10、F22（agent 自误判），加上本报告的 U2/U3/U4/U8 四类体验缺口——**一次 92 分钟的真实使用**就把"每次都会疼"的问题全数暴露，且自带优先级（疼几次排多前）。
- **审出来的**（三份评审）：F13（key 泄露）、F14（stop 无超时）、F15（alive 谎报）、F16（spill 不读）、F11/F17/F18/F8/F9——多为**低频高危**路径，一次正常使用根本踩不到；其中 F13/F14 属"疼一次就致命"。
- **效率对比**：使用型发现 ≈13 项/92 分钟且全是高频项；审查型发现 ≈9 项/数小时，覆盖尾部风险但需要真机使用来验证与排优先级（F15 的验收就反过来依赖真机）。
- **结论**：不是二选一——**先派使用型**（dogfood 定体验优先级与高频缺陷），**后派审查型**（扫安全与罕见路径）。顺序颠倒会把审查力气花在没人踩到的路径上；只有使用型则会漏掉 F13 这类静默泄露。本轮"边用边改 + 当天审查"的组合是有效的，应固化为惯例。

## 7. 结论：最关键 3 条 + 只能做一件
1. **U1 完成通知**（jobs + `owner.followup`）：一次性消灭 21 次轮询 + 4 个监视循环 + 人类的"你收得到吗"。
2. **U2+U3 额度闭环**：结构化失败推送 + 自动换号/降级，让 agent 不再关心余额、人类不再当调度员。
3. **U4 掐断可续**：产物强制落盘 + 同 thread 续跑，27 轮的工作不再蒸发。

**如果只能做一件：做 U1（A1 落地）。** 它是 U2/U4/U8 的共同前置——没有完成通知，降级、续跑、扇出全都要靠轮询拼起来；有了它，其余各项才有干净的触发点。
